# sql-monster 仕様

## 概要

SQLでモンスターを分析し、SQLで攻撃・防御する対戦ゲーム。`db-internal-app`(DBMS内部可視化の学習サイト)とは別アプリとして、モノレポ内に分けて置く。

---

## アーキテクチャ

**Project-Dの内部パッケージ(`executor`/`planner`/`txn`など)を`sql-monster`が直接importすることはしない。** 内部実装に直接手を突っ込む形になり、既存DBMSの使われ方(ワイヤープロトコルや公開C API越しにしか触らない)とズレるため。

代わりに、**Project-D側に新しく公開用の`client`パッケージ(仮称)を新設し、`sql-monster`はそれだけをimportする。**SQLiteが同一プロセス内で動きつつも公開されたCのAPIしか外部に見せないのと同じ考え方。

```go
db, err := client.Open(path)
tx, err := db.Begin()
result, err := tx.Exec(sql)   // Result に実行計画の情報(IndexScanだったか等)を含める
err = tx.Commit()
err = tx.Rollback()
```

HTTP API(`api/`)を拡張して複数リクエストにまたがる`BEGIN`/`COMMIT`を実現する案も検討したが、そのためには「誰のトランザクションかをリクエストをまたいで覚えておく」セッション管理が新たに必要になり(以前、自動コミット方式を選んだ際に保留にした問題)、`sql-monster`が同一プロセス内のGoプログラムとして動く前提なら不要な複雑さになるため見送った。

**`client`パッケージの新設はProject-Dコア側の作業であり、`sql-monster`固有の話ではない。** 実装済み(PR #6)。

`sql-monster`は`client`パッケージをimportし、その上に独自のHTTP API(フロントエンド向け)を被せる二層構成にする。パッケージ構成はコアの`cmd/server`に揃え、`sql-monster/internal/game/`(コアロジック)+`sql-monster/cmd/server/`(エントリポイント)とする。

**暫定措置: 現在のDBエンジンはSQLite。** Project-D本体のSQL言語に算術演算子(`+ - * /`)が未実装で、「`UPDATE monsters SET hp = hp - 50`」のような攻撃SQLが書けない(`project_issues.md`参照)。これを回避するため、`sql-monster/internal/sqlitedb`パッケージ(`database/sql` + `modernc.org/sqlite`)を新設し、`client`パッケージの代わりに一時的に使っている。`client.DB`とほぼ同じメソッド形状(`Open`/`Exec`/`Begin`/`Tx.Exec`/`Commit`/`Rollback`)にしてあり、Project-D本体に算術演算子が実装され次第、`client`パッケージに戻す想定。上記の二層構成という設計方針そのものは変わっていない。

## モンスター

モンスターごとにテーブルが用意される。レベルに応じて、カラム構成・クエリの難易度が変わる。

- **低レベル**: 弱点や攻撃の「出やすさ」を表す明示的なカラムがある。単純な`SELECT`で分析できる。
- **中レベル**: 弱点や攻撃の手がかりが複数テーブルに分かれている。`JOIN`が必要。
- **高レベル**: 集計・条件分岐・過去ログの傾向分析が必要。ダミーの手がかりが混じることもある。

---

## 1ターンの流れ

4フェーズで構成する。

```
① 攻撃用分析 → ② 攻撃 → ③ 防御用分析 → ④ 防御
```

### ① 攻撃用分析

モンスターの弱点データに対して`SELECT`を実行し、弱点を調べる。分析リソースを消費する(下記)。

### ② 攻撃

弱点を突く`CRUD`文でモンスターに攻撃する。SQLの操作の種類がそのまま技の種類に対応する。

| SQL操作 | 技のイメージ |
|---|---|
| `UPDATE ... SET hp = hp - X WHERE ...` | 直接攻撃 |
| `INSERT INTO status_effects (...)` | 状態異常付与(毒など) |
| `DELETE FROM buffs WHERE ...` | モンスターの防御バフ・シールドを剥がす |

**ダメージ量の決定方法:** プレイヤーがクエリに書いたリテラル値をそのまま信用しない。実際にトランザクション内で実行し、実行前後のHP差分を実測する。

```
1. CRUD文をトランザクション内で実行する
2. 実行前後のHP差分(実際に何点減ったか)を測る
3. 差分が攻撃防御リソースの残量を超えていたら ROLLBACK(不発)
4. 収まっていれば COMMIT して、差分ぶんだけ攻撃防御リソースを消費する
```

`WHERE`が緩く余計な行まで巻き込むと、その分HP差分の合計が増えて損をする。狙いが精密なクエリ(現状はPKへの等値検索でIndexScanが選べるもの)ならクリティカルヒットになる。効率判定の基準は「クエリオプティマイザのロードマップ」(project_issues.md参照、PK判定 → セカンダリインデックス → コストベース最適化)に従って将来的に拡張する。

### ③ 防御用分析

モンスターの今ターンの攻撃を推測するための手がかりテーブルを`SELECT`で読む。レベルに応じて手がかりの複雑さが変わる。

| レベル | 手がかりテーブル例 |
|---|---|
| 低 | `monster_attacks(id, monster_id, name, tag, likelihood)` — 出やすさを直接持つ |
| 中 | `monster_state(monster_id, hp_percent, is_enraged, ...)` + `attack_triggers(attack_id, condition_column, condition_value)` — 状態と発動条件を`JOIN`して推測 |
| 高 | `attack_history(battle_id, turn, attack_id)` も絡めて過去の傾向を読む。ダミーの条件も混ざる |

「今ターンの実際の攻撃」はどのテーブルにも書かない。ゲーム側(Goのメモリ)だけで保持し、DBには一切公開しない。

### ④ 防御

③の分析結果をもとに、`monster_attacks`に対してWHERE付きの`SELECT`を実行する。これが最終的な防御行動になる。

**判定:**

```
ブロック率 = 1 / (自分のWHEREで該当した行数)
```

返ってきた行の中に「今ターンの実際の攻撃」が含まれていればブロック成立。含まれていなければブロック率0(フルダメージ)。

- 1つに絞って的中 → ブロック率100%(0ダメージ)、精密な的中としてHP増加ボーナス(ゲーム側が自動付与)
- 複数タグを保険で並べて的中 → ブロック率は該当行数分の1に低下

③④はどちらも`SELECT`(読み取りのみ)なので、両方とも分析リソースだけを消費する。攻撃防御リソースは②の攻撃でのみ使う。

## リソース

2種類。毎ターン開始時に上限まで全回復する(持ち越しなし)。

| リソース | 消費対象 | 消費量 |
|---|---|---|
| 分析リソース | ①③④(すべての`SELECT`) | 読んだ行数の合計 |
| 攻撃防御リソース | ②(攻撃のみ) | トランザクションで実測したHP差分の合計 |

**攻撃防御リソースが尽きた場合:** その行動は実行できない(何も起きない)。特別なペナルティはなく、次ターンで全回復する。

**難易度スケーリング:** モンスターのレベルが上がるほど、両リソースの上限を絞る。無駄なクエリが許されなくなり、精密さが要求される。プレイヤー側のレベル成長による変化は現時点では設けない。

---

## 勝敗条件

プレイヤーのHPが0になったら敗北。モンスターのHPが0になったら勝利。

**バトルの構成:** 1体のモンスターと決着がつくまでの対戦。連戦(複数体を順番に倒す構成)はしない。
