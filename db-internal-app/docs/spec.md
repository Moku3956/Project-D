# db-internal-app 仕様

## 概要

Project-DにSQLを投げると、`lexer → parser → planner → executor → storage`の各ステージで何が起きているかを1ステージずつ「次へ」で確認できる学習サイト。SQLの内部処理を可視化できるサービスが存在しないことが動機([[project_overview]]参照)。

自由入力プレイグラウンド形式。ユーザーはCREATE TABLE/INSERT/SELECT/UPDATE/DELETEなど任意のSQLを打ち込める(sql-monsterのような固定シナリオではない)。

### スコープ: Lexer・Parser・Plannerは現時点スコープ外(ユーザー確定済み)

5ステージのうち、**実際に見せる価値が大きいのはExecutor(実行順序)とStorage(B+Treeの変化)**。Lexer/Parser/Plannerの3つは「トークン列やASTやプランツリーをただ表示するだけでは、見せられても学びが薄いのでは」という疑問が出た。

Figmaのモックアップ自体は5ステージ分とも残すが、**実装フェーズではLexer/Parser/Plannerをスコープ外とし、Executor/Storageを優先して作る。** 将来的にLexer/Parser/Plannerを実装する場合も、「ただ中間表現を出す」以上の見せ方(何が学べるか)を先に詰め直す必要がある。

## アーキテクチャ

**sql-monsterとは異なり、`client`パッケージ経由では実装できない。** `client.Exec`は最終的な`Result`(行データ・影響行数)しか返さず、lexerのトークン列やASTやプランツリーといった中間表現を外に出さない設計になっている(`client/client.go`確認済み)。可視化が目的である以上、db-internal-appは`sql/lexer`・`sql/parser`・`sql/planner`・`executor`・`storage/btree`・`storage/page`を直接importする。

これはCLAUDE.mdの「`client`経由でしか触らせない」という方針からの意図的な逸脱であり、sql-monsterとは別の理由(内部可視化そのものが目的)による。sql-monster/docs/spec.mdの「既存DBMSの使われ方に揃える」という理由はここには適用されない。

### ストレージ可視化は既存コードへの侵襲的な変更を避ける

B+Treeのページ/ノード単位のツリー図まで見せる(ユーザー確定済み)。当初「splitやinsertの過程をフック/トレースで逐次記録する」案も考えたが、`storage/btree`は本体サーバー・sql-monster双方が使う共有エンジンであり、そこにトレース用のフックを埋め込むのは挙動・性能両面でリスクが高い。

代わりに、**クエリ実行の前後でB+Treeの全ページを`RootPageID`からルートダウンに辿って読み、シリアライズ可能なツリー構造(ページID・種別・キー一覧・子ページID一覧)にダンプする、新規の読み取り専用メソッド**を`storage/btree`に追加する(既存の`Search`/`Insert`/`Delete`/`Scan`には一切手を入れない)。フロントエンドは実行前後のダンプを見比べて「どのページが変わったか(分割が起きたか等)」を表示する。ページ内部(スロット配列・セルバイト列)まで見せるかは次項参照。

**実装済み(`storage/btree/dump.go`、`(*BTree).DumpTree`)。** 当初`disk *page.DiskManager`を直接読む自由関数として設計していたが、`storage/btree/docs/spec.md`のNo-Force方式(コミット後もバッファプール上のdirtyページが最新で、ディスクにはまだ反映されない場合がある)を踏まえると、`disk`を直読みすると未フラッシュの変更を見逃すバグになると気づき、既存の`Search`/`Scan`と同じく`bt.bp`(バッファプール)経由で読む`*BTree`のメソッドに変更した。この見逃しは`TestDumpTreeReflectsUncommittedInsert`で回帰確認している。

また、1つのB+Treeファイルは複数テーブルのセルを同じページに混在させて保持しうる(`storage/btree/docs/spec.md`「キーフォーマット」参照)ため、葉ノードのセルは`schema.TableID`に一致するものだけを`Rows`に含める(`Scan()`と同じ判定方法)。

```go
// storage/btree/dump.go
func (bt *BTree) DumpTree(schema *types.Schema) (*TreeSnapshot, error)

type TreeSnapshot struct {
    RootPageID uint32
    Pages      map[uint32]PageSnapshot
}

type PageSnapshot struct {
    PageID         uint32
    IsLeaf         bool
    Keys           []string    // 内部ノード: 複合キーを人間可読な形にデコードしたもの
    ChildPageIDs   []uint32    // 内部ノードのみ(Key_iとChild_(i-1)の対応も含む)
    RightmostChild uint32      // 内部ノードのみ
    Rows           []types.Row // 葉ノードのみ。KVそのもの(スロット配列・オフセット等の内部形式は含めない)
    NextLeafID     uint32      // 葉ノードのみ
}
```

## 操作モデル

1. ユーザーがSQLを1文入力して実行する
2. サーバーは`lexer`→`parser`→`planner`→`executor`→`storage`の全ステージ分の情報を**1回のHTTPレスポンスにまとめて**返す(WebSocketは使わない。[[project_overview]]の既存方針を踏襲)
3. フロントエンドは受け取った全情報を保持したまま、「次へ」ボタンで1ステージずつ画面に開示していく(ガイド付き体験。ユーザー確定済み)
4. 各ステージの詳細は下記「ステージごとの表示内容」を参照

**デモ用テーブルはユーザーに作らせず自動で用意する(ユーザー確定済み)。** 「テーブルをユーザーに実装させる(CREATE TABLEを手で書かせる)必要があるか?」という問いに対し、Storage可視化のデモとして使う`users`テーブルは、フロントエンドがセッション開始時(ページロード時)に自動でCREATE TABLEする。既に存在する場合(戻ってきたセッション)はcatalogの"table \"users\" already exists"エラーを無視して現在の木を取得し直す。「リセット」ボタンを押した後も同様に自動で作り直す。ユーザーが最初に触るのはINSERT文(エディターの初期表示)からで良く、CREATE TABLEという手順自体を意識させない。もちろん自由入力プレイグラウンドである以上、ユーザーが自分で別のCREATE TABLEを書くことは引き続きできる。

### セッションの永続性

**将来的に一般公開し、不特定多数が同時に触れるデモサイトにする想定(ユーザー確定済み)。** この前提により、DBインスタンスをセッション単位で分離する設計が必須になる(誰かのDROP TABLEが他人の画面に影響してはいけない)。

CREATE TABLEしたテーブルにその後何度もINSERTし、B+Treeが分割で育っていく様子を見せることが、ストレージ可視化の一番の見せ場になる。そのためには**同じセッション内で複数クエリをまたいでDBの状態が保持される**必要がある(1クエリごとにDBをリセットする方式だと、2回目以降のINSERTでの分割が観察できない)。

**設計:**

1. **Cookieベースのセッション。** 初回アクセス時にランダムなセッションID(UUID)を発行し、`HttpOnly`+`SameSite=Lax`のCookieとして返す。以降のリクエストはこのCookieでセッションを識別する(sql-monsterのようにフロントエンドが1プレイヤー=1プロセス想定ではないため、この点はsql-monsterと構成が異なる)。
2. **セッションごとに専用の一時ディレクトリ**(`page.DiskManager`+`wal.WALManager`+`catalog.Catalog`一式)を、初回クエリ実行時に遅延作成する。サーバープロセスは`sessionID → *DB`のin-memoryマップを保持する。sql-monsterの`DATA_DIR`衝突バグ([[project_issues]]参照)と同じ轍を踏まないよう、db-internal-app用のディレクトリも本体サーバー・sql-monsterとは独立させる。
3. **アイドルセッションの掃除。** 一定時間(例: 30分)操作のないセッションは、バックグラウンドの定期処理でディスク上のディレクトリごと削除し、in-memoryマップからも破棄する。公開デモである以上、放置されたセッションでディスクが際限なく埋まることを防ぐ必須の仕組み。
4. **「リセット」ボタン。** ユーザーが明示的に今のセッションのDBを閉じて空の状態から作り直せるようにする。

**公開デモとして必要なリソース制限(実装時に具体値を詰める):**
- セッションあたりのページ数上限(容量の上限)を設け、超えたらエラーで拒否する
- サーバー全体の同時セッション数に上限を設け、超えた場合は最もアイドルなセッションから追い出す
- 1クエリあたりの実行タイムアウト

具体的な数値(タイムアウト秒数、ページ数上限、同時セッション数上限)は実装フェーズで決める。

## UIビジュアルスタイル

明るい色を基調とした、しゃれたスタイルにする(ユーザー確定済み)。sql-monsterのダーク基調・ゲーム的な見た目とは対照的な方向性。

**配色は「Sky Coral」に確定(Figmaで複数案から選定済み)。** アクセント: `#2FB4FF`(スカイブルー)+ `#FF7A59`(コーラル、新規/注目箇所のハイライト用)。背景`#F3FAFF`・サーフェス`#FFFFFF`・本文`#10243E`・ミュート`#7C93A8`・枠線`#D8E9F5`。Figmaファイル「データベース可視化」に`db-internal-app colors`という変数コレクションとして定義済み。

**画面レイアウトは60:40の2カラム(ユーザー確定済み)。** 左60%にステージのステッパー+その時点のステージ内容、右40%に常時表示のSQLエディター(複数行のテキストエリア+実行ボタン)を置く。sql-monsterのMonsterPanel/WorkspacePanelの60:40分割と発想は近いが、db-internal-appでは「エディターが常に右側に固定」という構成にした。想定キャンバス幅は1200px程度(フルスクリーンではない、通常のブラウザウィンドウサイズを想定)。

**日本語/英語の切り替えに対応した(ユーザー確定済み)。** 「JapaneseとEnglishの切り替えができるようにしよう」というユーザー指示による。`shared/i18n.ts`にキー→{ja, en}の対訳辞書と、現在の表示言語を保持するZustandストア(`useLocaleStore`)を実装した。`{name}`形式のプレースホルダー置換にのみ対応する簡易実装で、外部i18nライブラリは導入していない(文字列数が少なく、複数形/日付フォーマット等の複雑なルールが不要なため)。

- 初期値は`localStorage`に保存済みの言語があればそれを使い、なければ`navigator.language`から自動判定する(日本語ブラウザなら`ja`、それ以外は`en`)。切り替え後の選択は`localStorage`(キー`db-internal-app:locale`)に保存し、次回訪問時も引き継ぐ。セッション(サーバー側の`db_internal_sid`)とは無関係の、純粋にブラウザ側だけの表示設定。
- 切り替えUIは`TopBar`の右上に「JA / EN」の2択ピルとして配置し、「リセット」ボタンの隣に置いた。
- 対訳対象はUIの固定文言のみ。テーブル名・SQL文・エラーメッセージ(バックエンドの`error`文字列)・カラム名は対訳しない(ユーザーが入力した実データ・SQLの構文エラー文言まで翻訳するのはスコープ外)。

## ステージごとの表示内容

### ① Lexer 【現時点スコープ外】

トークン列をそのまま返す。`sql/lexer`の`Token{Type, Literal, ...}`を配列で見せる。SQL文字列の該当範囲をハイライトできるよう、位置情報(あれば)も含める。

### ② Parser 【現時点スコープ外】

`sql/ast`のASTをツリー表示する。`sql/docs/ast.md`に定義された各ノード型(`SelectStmt`/`InsertStmt`/`BinaryExpr`等)をJSONにシリアライズし、フロントエンドでツリー図として描画する。

### ③ Planner 【現時点スコープ外】

`sql/planner`の`PlanNode`ツリーをそのまま表示する。`sql/docs/planner.md`のプランツリー例(`ProjectionNode → FilterNode → SequentialScanNode`等)と同じ形。IndexScanかSequentialScanかの選択理由(PK等値/範囲条件の有無)もあわせて表示し、「なぜこのスキャン方式が選ばれたか」が伝わるようにする。

### ④ Executor

プランツリーと同型のExecutorツリーを表示し、各ノードが`Next()`で何行処理したか(最終的な行数、および可能なら先頭数行のサンプル)を添える。Volcano modelの「上のノードが下のノードを1行ずつ引っ張る」という実行順序自体を逐次アニメーションで見せることはしない(ユーザー確定済み)。「木構造＋各ノードの入出力行数」の静的な表示に留める。

### ⑤ Storage

**「テーブル」と「B+Treeページ構造」を並べて対比する(ユーザー確定済み)。** 「まずはinsertして、テーブルがどうなるのかを見せるべき。その中身が本当は、こうなってますよっとDBの中身って感じで見せるべき」「テーブルを表示したい」というユーザー指示により、B+Tree図の上に普通の行・列のテーブル(`DataTable.tsx`)を追加した。列は選択中テーブルのスキーマから動的に決まる(後述の複数テーブル対応により`id`/`name`固定ではなくなった)。データソースはB+Tree図と同じ`TreeSnapshot`(全葉ページのRowsを集めてPKでソートするだけ)で、省略はせず全件表示する。表示用の値の整形(`stripPadding`によるパディング除去)は`features/storage/displayValue.ts`に切り出し、`layout.ts`とテーブル表示の両方で共有する。「見た目はただのテーブルですが…」→「実際はこうやって保存されています」という対比の文言で、普段目にする表形式と内部のページ構造のギャップを伝える。

**複数テーブルに対応した(ユーザー確定済み)。** 「1つのテーブルだけじゃもったいない、複数のテーブルのB+Treeにしよう」というユーザー指示による。ストレージ層は元々`[tableID][type_tag][pk_bytes]`という複合キーで複数テーブルを1つの物理B+Treeファイルに同居させる設計であり、`DumpTree`もテーブルごとに`schema.TableID`でフィルタする作りだったため、**バックエンドの追加変更はテーブル一覧を返すAPIのみ**で済んだ(`Session.Tables()` → `GET /api/tables`。`catalog.Catalog.TableNames()`は元々存在していた)。フロントエンドには選択中テーブルを切り替えるタブ(`TableTabs.tsx`)を追加し、テーブル名をクリックするとそのテーブルの`SELECT * FROM <table>`を実行してデータ・木を取り直す(`switchTable`)。新しいテーブルの作成は専用フォームを設けず、既存の「自由入力SQLエディター」でそのまま`CREATE TABLE`文を実行させる方式にした(このアプリのそもそもの設計方針「自由入力のSQLプレイグラウンド」に沿う)。タブバーの「+ 新しいテーブル」ボタンは`t1`, `t2`, ...という連番の名前でCREATE TABLE文を**即実行**し、作成したテーブルに切り替える(`createTable`)。当初はエディターにひな形を入力するだけで実行はユーザー任せにしていたが、「勝手にクエリを実行すればいいのでは？」というユーザー指示により即実行に変更した。SQL実行のたびにテーブル一覧を取り直す(`run`・`createTable`内で`listTables`を呼ぶ)ことで、CREATE/DROP TABLEした結果をタブバーに反映する。「まとめてINSERT」(`seedMany`)は`id`/`name`の2カラム(`users`と同じ形)を仮定したままで、他の形のテーブルに対しては実行時にSQLエラーとして表示される(専用の汎用ダミーデータ生成は今回のスコープ外)。「+ 新しいテーブル」の裏側で実行するCREATE TABLE文はエディターの`sql`状態には反映しない(自動生成された裏側のクエリでユーザーの書きかけの入力を消してしまわないよう、`createTable`はローカル変数だけで完結させる。「新しいテーブルを作ったあとに、クエリをエディターに表示さしなくていいです」というユーザー指示による)。

**`TableTabs`はStorageCard(左)ではなく2カラム行の外側に置く(ユーザー確定済み・修正)。** 当初は左カラムの中に`<TableTabs /><StorageCard />`と縦に並べていたが、これだと右カラムの`EditorPanel`にはタブ分のオフセットがなく、「Editor, B+Tree Page Structureの上の辺がずれてる」という見た目のズレが生じていた。`TableTabs`を2カラムの`flex`行より上、`TopBar`のすぐ下に移動し、両カラムの先頭カード(`StorageCard`と`EditorPanel`)が同じY座標から始まるようにした。

**リーフノードにテーブル名ラベルを付けた(ユーザー確定済み)。** ストレージ層は1つの物理B+Treeを全テーブルで共有しており、`DumpTree`は選択中テーブルの`schema.TableID`と一致する行だけをRowsに残す(ルート・内部ノードの構造自体はフィルタしない)。そのため、新規作成した空のテーブルを見ても、既存テーブルの行で分岐した内部ノード構造がそのまま辿られ、リーフの中身だけが軒並み「(空)」になる、という紛らわしい見た目になっていた(「new_tableのページが(空)になってます」というユーザー指摘)。バックエンドのフィルタ処理自体は変えず(他テーブルの行を露出させる本格対応は今回のスコープ外、ユーザーが軽量案を選択)、**フロントエンド側でリーフの箱の中に選択中テーブル名を小さなラベルとして表示する**ことで、「このページは今このテーブルの行だけを表示しているのだ」と分かるようにした(`TreeDiagram.tsx`の`LeafBox`、`layout.ts`の`LEAF_LABEL_H`)。ラベル分の高さはリーフボックスの下方向に拡張するだけなので、既存の縦位置計算(`INTERNAL_H + LEVEL_GAP`ベース)には影響しない。

**↑のラベルは「実際にそのテーブルの行を含むページ」にだけ付ける(修正の第一段階)。** 当初は選択中テーブル名を**全リーフに無条件で**表示していたが、「リーフノードのすべてに新しいテーブルの名前が書かれます。問題です」というユーザー指摘の通り、これは誤り。1つの物理木を全テーブルで共有しているため、`cells`が空(=選択中テーブルの行が1件もない)のページは実際には他テーブルの行で埋まっている可能性が高く、そこに選択中テーブル名を書くのは「この空ページは自分のものだ」という誤った印象を与えてしまう。`LeafBox`で`cells.length > 0`の場合だけテーブル名を表示し、空の場合は`?`を表示するよう修正した(60件シードした`users`と1件だけの新規テーブルで実機確認)。

**最終的にバックエンドのフィルタ処理自体をやめ、ページ内の全テーブルの行をテーブルごとにグループ分けして表示する方式にした(ユーザー確定済み・本格対応)。** 上記の`?`表示は「他テーブルの行がある」ことは示せても「どのテーブルの行か」「同じページに複数の他テーブルが混在しているか」までは分からなかった。「同じページの中にも違うテーブルのレコードが含まれることがあるので、その場合も分けましょう」というユーザー指示により、以前見送っていた本格対応(選択肢アンケートで一度は「軽量: ラベルだけ追加」を選んでいたが、実際に使ってみて限界が判明したため方針転換)に切り替えた。

- `storage/btree.BTree.DumpTree(schemas map[uint32]*types.Schema)`: 引数を単一の`*types.Schema`からtableID→Schemaの全件マップに変更。葉セルのデコード時に**そのセル自身のtableID**に対応するschemaを使うようにし、`schemas`に存在しないtableIDのセルだけ無視する(以前のような「選択中テーブル以外を除外」はしない)。`PageSnapshot`に`RowTables []string`(`Rows`と同じ長さ・並び順で、各行がどのテーブルのものかを示す)を追加。
- `db-internal-app/internal/dbsession.Session.DumpTree(table string)`: `table`は「そのテーブルが存在するか」の検証にのみ使い(存在しなければ従来通りエラー)、返す内容自体は物理木全体(全テーブル・全行)で、`table`の値によって変わらない。
- `GET /api/exec`のレスポンス(`pageSnapshotJSON`)に`rowTables`を追加。
- フロントエンド`layout.ts`: `rows`を`rowTables`(並行配列)で「同じテーブルが連続する区間」ごとにグループ化する(`groupByTable`)。複合キーはtableIDを先頭に持つため、同テーブルのセルはページ内で連続しており、隣接比較だけで正しくグループ化できる。1グループ=1つの`LeafGroup{ table, cells }`とし、`LayoutNode.cells`は`LayoutNode.groups`に置き換えた。グループごとに独立して「先頭2件+省略+末尾2件」の省略表示を適用する。
- `TreeDiagram.tsx`の`LeafBox`: グループごとに[テーブル名ラベル]+[KVセル列]を横に並べて描画し、グループ間は太めの区切り線で分ける。選択中テーブルのグループは通常表示、それ以外のグループは淡色(`opacity`を下げた配色)にして「他テーブルの行」と視覚的に分かるようにする。
- `DataTable.tsx`・`store.ts`(`collectPKs`/`diffNewPKs`/`maxNumericId`): これまでは`page.rows`が選択中テーブルの行だけという前提だったが、フィルタをやめたことで他テーブルの行も混ざるようになったため、`rowTables[i] === table`で絞り込む処理を追加した。

実機確認: `users`に2件(`alice`, `bob`)だけ入れてsplitさせず、直後に新規テーブル(`t1`)を1件(`apple`)だけ挿入すると、両者が**同じ1枚のリーフページ**に収まる。この状態で`t1`を表示すると、リーフ内に「users(淡色): alice, bob」「t1(通常色): apple」という2つのグループが並んで表示され、テーブル境界が正しく分かることを確認した。「テーブル」タブ(`DataTable`)側も`t1`の行(`apple`)だけが表示され、`users`の行が混入しないことを確認した。

**Figmaでの検討を経て、木構造の描き方を確定した(詳細は下記)。** クエリ実行前後の`TreeSnapshot`(上記)を比較表示する。

**ツリーの見た目:**
- 内部ノード(Root等)から各ページへは、直角に折れた線ではなく**直線**でつなぐ(ユーザー確定済み。「枝を折るんじゃなくて直線に」)
- 分岐の条件(`< 5`・`>= 5`等)は縦線上ではなく、**分岐点の横一直線上**にラベルとして置く。`key: 5`のようなルートの分割キーも同様に、ルード直下の線上に配置する
- 内部ノードは今のところRootのみ(1回のsplitしか起きていない例のため)。ページが増えて内部ノードが複数階層になった場合の見た目は別途検討が必要(未定事項参照)

**ページの中身(KV)の見せ方:**
- 1ページはKVを**横に並べたセル区切りのボックス**で表現する(セルの縦積みではなく横並び。ユーザー確定済み)
- 新規に追加されたKV(INSERT等で増えた行)だけをハイライトする。ページ全体を「新規ページ」として塗るのではなく、**変化した行そのもの**を強調する方が正確(既存の行がページを移動しただけの場合と区別できる)

**KVが多いページの省略表示(ユーザー確定済み):** 1ページ(4KB)に入るレコード数を`storage/btree/cell.go`のセルフォーマットから実際に計算すると、`id INT PRIMARY KEY, name VARCHAR(50)`程度のスキーマで**約50〜116件**(名前の長さによる)。この件数を横一列のセルでそのまま並べると画面に収まらないため、**先頭2件＋省略(`…N件…`)＋末尾2件**という形で省略表示する。省略チップは「拡大表示」に対応し、ページのレコード数が閾値(先頭2件＋末尾2件=4件)を超えた場合にのみ適用する。3件以下ならそのまま全件表示する。

**「拡大表示」ボタン(実装済み)。** B+Treeはこのアプリの一番の見せ場のため、コンパクトなステージ画面とは別に、フルスクリーンでツリー図全体を表示するビューを用意した。

当初はFigmaのキャンバス操作に近い、ホイールで拡大縮小(カーソル位置基準)・ドラッグでパンする自由なズーム/パンを実装したが、「ちゃんと動かない」「Figmaみたいにしなくても大丈夫、ツリー全体が見えるようにしよう」というユーザー指示により、**手動操作なしで常にツリー全体が画面に収まるよう自動縮小する方式(`FitToScreen`)に作り直した**。表示領域とツリー図の自然な大きさ(`content.scrollWidth`/`scrollHeight`。`transform: scale()`はレイアウト計算に影響しないため、縮小率に関係なく常に自然な大きさが取れる)を比べて縮小率を決める。領域より小さい場合に無理に拡大はしない(縮小のみ)。手動ズーム/パン用のコード(`ZoomPanCanvas`)は削除した。

**その後、「拡大できる制限があり、思うように拡大できない」というユーザー指摘により、shrink-onlyだった`FitToScreen`に手動ズームを追加した。** 開いた直後は上記の自動フィット(=最大100%、縮小のみ)を初期値として使うが、そこから先は下部中央に浮かせた「−／100%／＋／Fit」の操作バーで、10%〜400%の範囲で自由に拡大・縮小できる。前回「ちゃんと動かない」と指摘された独自のホイール/ドラッグ処理を再導入するのは避け、**パン(拡大してはみ出た分の移動)はブラウザ標準のスクロールに任せる**設計にした(コンテナに`overflow-auto`をかけ、拡大後の実サイズ分のスクロール領域を用意するだけ。独自のポインタイベント処理は増やしていない)。「Fit」ボタンで自動フィット時の縮小率にいつでも戻せる。

**シードデータをわざと大きくして、少ない件数で本当に分岐する木を見せる(ユーザー確定済み)。** 1ページ約50〜116件という実測値のままだと、数百〜数千件入れない限りRoot+葉2枚という浅い形にしかならず、「ツリー構造の可視化」として物足りない。一方でPageSizeは`storage/page`側で`[PageSize]byte`という固定長配列(コンパイル時定数)になっており、db-internal-app側だけ小さくすることはできない(storage/btreeのバイトオフセット計算全体が前提にしており、変えるとsql-monster・本体サーバーにも影響するため不可)。

代わりに、**VARCHAR(50)という宣言が実際には`sql/planner`・`executor`のどこでも検証されていない**(project_issuesの既知の課題「型チェック未実装」)ことを利用し、フロントエンドの「まとめてINSERT」機能(`seedMany`)が生成するダミーの値をわざと長くパディングしている。**ストレージエンジン自体には一切手を入れておらず、あくまで「実際に入れるデータの大きさ」で1ページの実効容量を調整している点が重要**(spec.mdの「既存コードへの侵襲的な変更を避ける」方針を維持したまま)。

**「Rootが極端に横広がりになる」問題と、その修正(ユーザー確定済み)。** 当初は`name`列だけをパディングしていたが、これだと**内部ノードの容量が全く変わらない**ことが実機で判明した。内部ノードのセルは`[複合キー][子ページID 4byte]`のみで`name`等の他カラムを含まないため、`name`をどれだけ長くしても内部ノードは約193件のまま=Rootが極端に多くの葉を直接抱え込む横広がりの木になっていた。

複合キーは葉・内部ノードの**両方**に含まれるため、代わりに**主キー(id)自体を長くパディングする**方式に変更した。これにより葉・内部ノード両方の容量を一緒に下げられる。文字列PKは辞書順ソートされる(`storage/btree/cell.go`の`compareValues`)ため、"id-2" < "id-10"のような直感に反する並びを避けるべく、id生成時に数値部分を6桁ゼロ埋めしてからパディング文字を続けている(`paddedSeedId`)。

現在のスキーマ: `id VARCHAR(600) PRIMARY KEY, name VARCHAR(50)`。`name`はもうパディングせず実際の短い値(`seed-N`)をそのまま入れる。

表示側(`features/storage/layout.ts`)は個々のフィールド値を最大12文字に切り詰めて見せる(`truncateField`)。これは葉のKV表示だけでなく、**内部ノードの分岐ラベル(`< key`等)にも同様に適用する必要がある**(ラベルにパディング後の生の値をそのまま使うと600文字になってしまうバグを実機で発見・修正した)。実データの長さと画面上の簡潔さは別の話、というユーザー指示による。

実測値: 60件のシードで、葉は2件ずつ・内部ノードは4〜7件ずつに分岐し、Root配下にさらに中間の内部ノードが複数できる(合計8個の内部ノード)、という深さのある木になる。以前の「nameだけパディング」方式(40件で13個の葉が全てRoot直下、内部ノード容量は約193のまま)と比べて、明らかにバランスの取れた分岐になった。

**スロット配列・セルの生バイト列までは見せない(ユーザー確定済み)。** ページの中身がKVとして分かれば十分で、`storage/page`の内部フォーマットの詳細はスコープ外とする。`PageSnapshot`にオフセット・フリーリスト等の生の数値フィールドを含める必要はなく、`Keys`をKVのペア(`Values []types.Row`相当)に置き換える形でよい。

**「実データ」/「イメージ図(例)」の切り替えは廃止した(ユーザー確定済み)。** 一時、実データ(セッションのDumpTree結果)と架空の3階層`TreeSnapshot`(`exampleTree.ts`)を切り替えるトグルを用意していたが、「まずはinsertして、テーブルがどうなるのかを見せるべき。その中身が本当は、こうなってますよっとDBの中身って感じで見せるべき」というユーザー指示により削除した。idパディングのおかげで少ないINSERTでも十分に分岐した木が見えるようになったため、架空の例を別途用意する必要性も下がっている。画面には常にセッションの実データだけを表示する。トグルのラベルだった「実データ」という呼び方もやめ、「B+Tree ページ構造」の説明文だけで見せる形にした。
